# A machine-wide gate and ship log, with `guardrails stats` (#176)

## Problem

Nothing records how long a gate waited for the lock, held it, or spent in
Stryker, whether its mutation cache was seeded, or how a ship split its time
between gate, push and CI. `.guardrails/state/decisions.jsonl` holds only
`stop` rows, per checkout, with no timing. The dialed.run throughput review
rebuilt every number from transcripts, and five of its open trade-offs are
waiting on this data.

## What was found while planning

- **The JSON report is always there for a gate run.** `runStryker` passes
  `--reporters json` (with the progress reporter when locked) on the command
  line, overriding the adopter's `reporters`. So the "adopter hasn't enabled
  the json reporter" case can't arise inside the gate. It can only arise
  when the report is missing (a crash, or a kill). The row then says
  `report: "missing"`, as the issue asks.
- **The JSON report carries no timings.** A real report here has
  `schemaVersion`, `thresholds`, `projectRoot`, `config`, `framework` and
  `files`, with no `performance` block. Counts (mutants, timeouts,
  survivors) come from the report, and times come from the progress plugin,
  which already sees the lock taken (it writes the holder file), the plan
  ready (end of the dry run) and the report ready (end of mutation).
- **The lock wraps Stryker alone** (`runUnderLock`), so lock timings belong
  to the Stryker part of a gate row. A gate that ran no Stryker has no lock
  part.

## Design

**One file, one row per run.** It sits beside the gate lock, at
`<lock path>.runs.jsonl` (`~/.guardrails-gate.lock.runs.jsonl` by default,
following `GUARDRAILS_GATE_LOCK`). Rows are appended as single `write`s of
one line opened with `O_APPEND`, so concurrent gates don't interleave on a
local filesystem. There is no rotation: a row is about 1 KB, so a busy month
is a few MB. Every row has `v: 1`, and the reader skips lines it can't
parse. Writing the log never fails a gate or a ship: an error is one stderr
line.

**Gate rows** are written at the commit and push rungs on every run, and at
the stop rung only when Stryker was in scope. A stop turn with nothing to
mutate is noise, and there are hundreds of them.

```jsonc
{
  "v": 1, "kind": "gate", "rung": "push", "repo": "dialed.run",
  "branch": "w15-sec-l23", "ship": "<id or absent>",
  "startedAt": "…", "finishedAt": "…", "outcome": "pass|block|defer|lock-timeout",
  "lock": {                       // absent when Stryker did not run
    "queuedMs": 812000, "heldMs": 1460000,
    "holderOnArrival": "dialed.run (push), mutating 120/400", "depthOnArrival": 2
  },
  "stryker": {                    // absent when nothing was in scope
    "files": 3,
    "cache": { "local": "kept|none|discarded", "seed": "used|refused|not-needed|off",
               "why": "different dependency versions" },
    "dryRunMs": 95000, "mutatingMs": 1300000,
    "mutants": 412, "reused": 380, "timeouts": 6, "survivors": 0, "noCoverage": 0,
    "report": "read|missing"
  },
  "machine": { "cores": 10, "concurrency": "default|<n>",
               "start": { "load1": 6.1, "freeMb": 2100 }, "end": { … } }
}
```

**Ship rows** have `kind: "ship"`, the same `repo`/`branch`/`machine`, plus
`pr`, `state` (the ship state) and `pushMs` (the `git push` wall time, gate
included), `gateMs` (read back from the gate row with the same `ship` id),
and `ciMs` (PR found to checks settled). Ship generates the id and passes it
to `git push` as `GUARDRAILS_SHIP_ID`; the pre-push hook inherits it, and
the gate stamps it on its row. That links the two rows without any
coordination.

**`guardrails stats`** reads the file and prints, for a window (`--since=7d`,
default 7 days) and optionally one repo (`--repo=<name>`):

- **Per rung:** run count; queue wait and hold time (median, p90); dry-run
  and mutating time (median, p90); seeded share, with the top reasons a run
  went cold.
- **Ships:** count by final state; median gate, push and CI time.
- **Concurrency:** median dry-run time by queue depth on arrival (0, 1, 2,
  3+) and by load at start. That's the plot the issue asks for, as a table.

`--json` prints the same summary as JSON for a coordinator to read.

## Steps

Each step is test-first, small, and green before the next.

1. **Log file.** `src/run-log.ts`: the row types, `runLogPath(lockPath)`,
   `appendRun(path, row)` (one line, `O_APPEND`, errors returned not
   thrown) and `readRuns(text)` (skips malformed lines and other `v`s).
   _Done:_ round-trip and malformed-line tests.
2. **Machine sample.** `sampleMachine()` with an `os` seam (load average,
   free memory, cores), and `concurrencyOf(strykerConfig)`: the configured
   `concurrency`, or `"default"`. _Done:_ pure tests.
3. **Plugin timings.** The progress plugin also writes
   `<lock>.holder.json`'s sibling `<repo>/reports/guardrails-run.json`, with
   the lock taken (`startedAt`), plan ready, report ready, and its counts. The
   path comes in the environment the locked run already gets.
   _Done:_ plugin tests on its event sequence; the drift test
   `stryker-runner.test.ts` asserts the file exists after a real run.
4. **Lock timing.** `runUnderLock` returns `queuedAt`, `releasedAt`, the
   first sighting's holder and depth (or none, when the probe found it
   free), with a clock seam. _Done:_ tests for free, busy-then-held, deferred
   and timed-out runs.
5. **Cache outcome.** `prepareIncrementalCache` returns what it did: local
   cache kept / none / discarded (and which fingerprint part, from #177's
   `fingerprintDifference`), seed used / refused (its reason) / not needed /
   off. `fetchSeed` returns its reason as data rather than only printing
   it. _Done:_ each existing cache test also asserts the outcome.
6. **Stryker part.** `runStryker` assembles the Stryker part from 3–5 and
   the JSON report's status counts (`report: "missing"` when it can't be
   read), and `runVerify` returns it on `VerifyResult`. _Done:_ orchestrator
   tests with a fake report and summary file.
7. **Gate rows.** `runCommitGate` and the stop gate append a row by the
   rules above, stamping `GUARDRAILS_SHIP_ID` when set. _Done:_ wiring
   tests in a temp lock directory: a push row with every part, a stop run
   with nothing in scope writes none, and an unwritable log still lets the
   gate decide.
8. **Ship rows.** `ship` generates the id, passes it to `git push`, times
   push and CI, reads its gate row back for `gateMs`, and appends its own.
   _Done:_ ship tests with the fake exec; #172, #175 and #178 behaviour
   unchanged.
9. **`guardrails stats`.** Pure `summarizeRuns(rows, window)` and a
   formatter; the command reads the file. _Done:_ summary tests on a fixed
   row set (medians, p90, depth buckets, cold reasons, ship splits);
   `--json`; an empty or missing log says so.
10. **Docs.** `docs/adoption.md` (the log, its path, `stats`), the CLI usage,
    and `upgrades/unreleased.md`.

## Not in scope

- Lock queue ordering (#147), aborting doomed runs (#148) and lock
  hardening (#149). This log is the data those wait on.
- Retention or rotation. Revisit if the file ever matters for size.
- Anything in dialed.run.

## Runtime cost

Per gate or ship: one `os` sample at the start and one at the end, one small
JSON file written by the plugin and read back, the JSON report read once
more for counts (it is already read for violations), and one appended line.
Milliseconds.
