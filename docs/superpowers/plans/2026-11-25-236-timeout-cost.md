# Plan: #236 steps 1–2 — measure what a Timeout costs, and confirm why

Stryker 10.0.0, vitest-runner 10.0.0. `core` = node_modules/@stryker-mutator/core/dist/src; `gc` = guardrails-core. Base: main @ 322f55d.

## Findings (spot-checked)

- **Per-mutant timeout** = `timeoutFactor × netTime + timeoutMS + timeOverheadMS` (`core/mutants/mutant-test-planner.js:124`).
- **`timeOverheadMS` = the dry run's gross time − the sum of per-test time** (`core/process/3-dry-run-executor.js:140-146`): for vitest, collecting/transforming the whole suite. It is added to _every_ mutant's timeout and cannot be configured. Under load the dry run inflates (25 min seen), so this term inflates every timeout. Wall time per timeout ≈ budget / concurrency, so a few minutes of overhead at concurrency 4 matches the observed ~150–190 s. A strong competing explanation to the restart hypothesis, and it would explain 4.5 h locally vs 40 min on CI.
- **A wall-clock Timeout does restart the worker** (`core/test-runner/timeout-decorator.js:47-48` "Timeout expired, restarting the process"): dispose (up to ~4 s), respawn, `createVitest` again, cold transform. **Hit-limit timeouts do not restart** (returned as an ordinary result).
- No event fires on a restart, and no per-mutant duration exists (core never sets `MutantResult.duration`). The plugin sees completions only, so per-mutant cost is exact only at concurrency 1 (the #202 re-test runs at 1).
- The plan event carries each mutant's `runOptions.timeout`. `onDryRunCompleted` gives `timing.net`/`overhead`. Injecting `'options'` gives the effective `timeoutMS`/`timeoutFactor`/`concurrency` (defaults, config and CLI alike, so it's consumer-generic).
- Gaps today: the #202 re-test overwrites the summary file and nobody reads it; unlocked runs load no plugin.

## Design

- **Plugin** (`stryker-progress-plugin.ts`): inject `'options'`; keep dry-run net/overhead; map Run-plan id → timeout budget; on each result (Run-plan ids only) classify as wall-clock / hit-limit / other, and add up the budget and the completion gap per class. Count wall-clock timeouts per file (repo-relative path, min/max line, top 5).
  - `RunSummary` gains `timeouts: {wallClock, hitLimit, budgetMs, wallClockGapMs, otherGapMs, byFile}` and `settings: {timeoutMS, timeoutFactor, concurrency, dryRunNetMs, dryRunOverheadMs}`.
  - The hit-limit predicate moves to a tiny shared module (the plugin must not import verify/).
- **Re-test**: delete the summary before run 2 and read it after. `retestMutatingMs` + `retestBudgetMs` give the **exact restart excess per timeout** in the field (it runs at concurrency 1).
- **Run log / stats**: nested `timeouts` + `settings` parts (defensive parsers; additive, so `v:1` stays valid).
  - `stats` lines: budget per timeout split into dry-run overhead vs the configured part; measured cost and excess from re-tests; settings tally; top files by wall-clock timeouts; share of mutating time ("estimate" when concurrency > 1).
- **Privacy**: per-file counts use repo-relative paths in the local run log only; nothing new leaves the machine.

## Choosing step 3 from the data

- Overhead dominates the budget → the lever is the dry run's overhead (#200) or a gate-side cap on the timeout (may need an upstream ask, since overhead isn't configurable).
- `timeoutMS`/factor dominate → gate-specific timeout settings.
- Re-test excess over budget is large (>30 s) → avoid the restart.
- byFile shows narrow clusters → recognise clusters.
