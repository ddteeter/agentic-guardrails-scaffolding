# 0.12.0 — what changed for an agent

## Behaviour that changed

- **One machine-wide lock now covers the stryker run, on every rung** (#146).
  The stop rung tries once and defers to commit. The commit rung waits
  `mutationLock.commitWaitSeconds` (60) and then defers to push, as a `warn`
  named `guardrails/mutation-deferred`. That warn means nothing to do: do not
  retry, and do not wait for the lock. The push rung waits `pushWaitSeconds`
  (10800) and then exits 75, which `guardrails ship` reports as
  `lock-timeout`. CI takes no lock.
- **`guardrails lock-status`** names the holder, its progress and the queue.
  A waiting run prints the same once a minute.
- **The PreToolUse commit gate checks staged files**, not the whole branch.
  An agent commit no longer re-runs stryker on every file the branch touched.
- **A reformatted owned file is not drift** (#143). `init --plan` used to
  read any guardrails-owned file your formatter had touched as hand-edited,
  and stopped upgrading it. It now compares words, not bytes, so a
  reformatted file upgrades like an untouched one.

## Instructions this supersedes

Search the repo's own instruction files for each phrase in the frontmatter.
A hit is not automatically wrong:

- A rule that serializes **mutation testing** by hand (`lockf`, `flock`, "one
  stryker at a time") can go: the lock does it. A lock that serializes
  something else stays.
- An instruction to **wait for or retry** a deferred mutation run is now
  wrong. Deferral is the design, and the push rung runs the deferred files.
- **`GUARDRAILS_GATE_LOCK_TIMEOUT`** in an env file or CI config still works.
  Moving it to `pushWaitSeconds` is tidier, not required.
- An instruction to re-run `init --apply --force` **because a formatter
  touched guardrails' files** is no longer needed. `--force` for a file
  someone really edited still is.

## What to wire

Nothing is required. If the machine runs long stryker jobs, consider
`mutationLock.commitWaitSeconds` and `pushWaitSeconds` in
`guardrails.config.json`.
